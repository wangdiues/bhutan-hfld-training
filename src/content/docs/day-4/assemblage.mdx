The <Term id="assemblage" /> is the last RLCMS stage. It turns the six <Term id="primitive">primitives</Term> (the probability layers for forest, cropland, grassland, other land, settlement and wetland) into one categorical land-cover map, using a **decision tree** whose thresholds and order you choose <Cite id="saah2020" />. This is where a national class system and forest definition are put into practice.

You can try the same logic, and see the Earth Engine rules it produces, in the [assemblage rule builder](/bhutan-hfld-training/labs/assemblage-builder/).

<Callout type="mistake" title="Assets you need">
The script loads the trainers' 2025 Sentinel-2 primitives (`projects/servir-mekong/bhutan_primitives/s2_<Class>_2025`) and uses a Landsat image only to define the area of interest. Without access, point the six paths to your own primitives from [Forest primitives](/bhutan-hfld-training/day-3/forest-primitives/) (each with a `target_probability` band from 0 to 1).
</Callout>

## Part 4: Settings

The order of `primitives` is the **priority order** of the rules, and `defaultThresholds` gives the probability each class needs before it is assigned:

<CodeBlock script="day-4/assemblage.js" lines={[59, 95]} />

| Priority | Primitive | Default threshold | Class code |
|---|---|---|---|
| 1 | forest | 0.50 | 1 |
| 2 | crop | 0.55 | 2 |
| 3 | grass | 0.55 | 3 |
| 4 | other | 0.60 | 4 |
| 5 | bu (built-up) | 0.30 | 5 |
| 6 | wet | 0.25 | 6 |

Rare classes such as built-up and wetland get lower thresholds, because their models are less confident even where they are right.

## Part 5: The decision tree

Two functions support the assemblage: one displays each primitive, and one turns the slider values into a decision tree in the text format that `ee.Classifier.decisionTree()` reads:

<CodeBlock script="day-4/assemblage.js" lines={[96, 156]} />

The tree is a chain of yes/no questions, in priority order:

1. Is forest ≥ 0.50? **Yes** → class 1 (forest). **No** → next question.
2. Is crop ≥ 0.55? **Yes** → class 2 (cropland). **No** → next.
3. … grass, other, built-up …
4. Is wet ≥ 0.25? **Yes** → class 6 (wetland). **No** → class 0 (unclassified).

<Theory title="Why the order matters" more="/explanation/rlcms-primitives-and-assemblage/">
A pixel can pass more than one threshold: forest 0.62 and crop 0.70, say. The tree stops at the **first** rule it passes, so this pixel becomes forest even though crop is more probable. Putting a class higher gives it priority in such conflicts. Changing the order, or a threshold, changes which class wins where primitives overlap, typically at edges, in agroforestry and in shrubland.
</Theory>

<Callout type="mistake" title="Corrected: class names in the area table">
The decision tree gives class 1 to the first primitive (forest), class 2 to the second (crop), and so on. The exercise's area table listed "Cropland" first, so the forest and cropland areas were swapped. The course script names the classes in the same order as `primitives`.

## Key functions

| Function | What it does |
|---|---|
| `ee.Classifier.decisionTree(string)` | A classifier from a decision tree written as text |
| `image.classify(classifier)` | Applies the rules to every pixel |
| `ui.Slider`, `ui.Button`, `ui.Textbox`, `ui.Panel` | Interactive controls in the Code Editor |
| `Map.onClick(callback)` | Runs code where the user clicks |
| `ee.Image.pixelArea()` | Pixel area in m², for class areas |
| `Export.image.toAsset({..., pyramidingPolicy: {'.default': 'mode'}})` | Exports a categorical map correctly |

## Common mistakes

- **Thinking the highest probability always wins.** With a rule chain, the first rule passed wins; order matters.
- **Thresholds set too high**, leaving many pixels unclassified (class 0). The course script masks class 0, so these show as gaps in the map: check for them.
- **Mismatched class codes and names** in legends and area tables (see the correction above).
- **Exporting a categorical map with the default (mean) pyramiding.** Zoomed-out views then show meaningless averages.

<Callout type="bhutan">
Bhutan context: the order and thresholds are a policy choice as much as a technical one. Putting forest first, with a threshold tied to the forest definition, makes forest win in mixed pixels; agroforestry and orchards then need care. Document the final order and thresholds: they are part of the method a verifier will check.
</Callout>

## Practice

<Challenge level="blanks" time={20} hints={["Settlement is 'bu'; cropland is 'crop'.", "Move 'bu' before 'crop' in both arrays.", "Class codes follow the order, so update the names in computeArea, the legend and the palette too."]}>
Settlements in Bhutan's valleys sit among fields, and the cropland rule often wins there. Give **settlement priority over cropland**: change `primitives`, `defaultThresholds` and the palette so built-up comes second, then re-run and compare the built-up area.

```js
var primitives = ['forest', '___', '___', 'grass', 'other', 'wet'];
var defaultThresholds = [0.50, ___, ___, 0.55, 0.60, 0.25];
```

<Fragment slot="solution">
```js
var primitives = ['forest', 'bu', 'crop', 'grass', 'other', 'wet'];
var defaultThresholds = [0.50, 0.30, 0.55, 0.55, 0.60, 0.25];
```
Class 2 is now built-up and class 3 cropland, so reorder `lcVis.palette` (`'267300', 'E600A9', 'AAFF00', …`) and `classNames` the same way. (The legend pairs each name with its own colour, so it stays correct.) The built-up area rises and cropland falls, mostly in mixed valley pixels.
</Fragment>
</Challenge>
